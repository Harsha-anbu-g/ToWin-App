# Submit config: the three values, and the one command that writes them

`eas submit` cannot deliver a build to either console until `eas.json` carries
three values that do not exist yet. None of them can be guessed, and none of
them exists before the accounts do. This page removes the hunting, so the day
the accounts open the job is a paste and a single command.

**Scope.** This page owns the shape of `submit.production` and the command that
writes it. The click paths around it live elsewhere and are linked, never
copied:

- `APPLE-DAY-ONE-RUNBOOK.md` part 5 for the whole iOS submit, flag by flag.
- `play-console-parallel-track.md` section "Service account JSON, step by step"
  for the six console steps that produce the Play key.
- `console-answers.md` for every console form field.

An empty `submit.production` is valid. `eas submit` reads it and asks for
everything interactively. That is the correct state until the real values
exist, because a placeholder identifier in a tracked file fails at submit time,
after a build has already been made.

## 2. The ordering trap, which is what stalls day one

The three values arrive in a fixed order. Skipping a step means waiting for the
step before it.

1. **Register the App ID `com.towinly.app`** at developer.apple.com, Certificates,
   Identifiers and Profiles, Identifiers, the plus button, App IDs, App. If the
   identifier is taken, stop here and change `app.json` before anything else.
   This is the last cheap moment to find a clash.
2. **Create the App Store Connect record by hand**, choosing that registered
   bundle identifier from the dropdown. It only appears in that dropdown after
   step 1. Do not let `eas submit` create the record: the automatic path names
   the app from `app.json`, which is the single word Towinly, and that is not
   the listing title.
3. **Now `ascAppId` exists.** It is generated by step 2 and by nothing else.

`appleTeamId` is available as soon as enrollment completes, so it does not wait
on this chain. The Play service account key has its own chain and waits on the
Play account, not on Apple.

## 3. The three values

| Value | Where it lives | Shape | Exists after |
| --- | --- | --- | --- |
| `ascAppId` | App Store Connect, open the app, **App Information**, right column, "Apple ID". The same number is in the app's console URL. | digits only, about ten of them | the app record is created |
| `appleTeamId` | developer.apple.com, **Account**, **Membership details**, the row called "Team ID" | exactly 10 characters, upper case letters and digits | enrollment completes |
| Play service account JSON | Google Cloud Console, **IAM and Admin**, **Service accounts**, the `eas-submit` account, **Keys**, **Add key**, **Create new key**, **JSON**. Reached from Play Console, **Setup**, **API access**. | a JSON file with `"type": "service_account"` and a `client_email` | the Play account exists and a Cloud project is linked |

Two values are worth having ready even though the CLI can ask for them:

- `appleId`, the email address of the Apple Account used to enroll.
- `sku`, the free text string typed when the App Store Connect record was
  created. It is never shown to users.

**Store the Play key outside this repository.** `~/.secrets/towinly-play-service-account.json`,
then `chmod 600`. The key can publish releases on the listing, so a committed
copy is a real leak. The script refuses a key that sits inside the app
directory.

## 4. The one command

```bash
cd "/Users/aghar/Documents/Projects/ToWin App/App"
npm run submit:config -- \
  --asc-app-id 1234567891 \
  --apple-team-id ABCDE12345 \
  --play-key ~/.secrets/towinly-play-service-account.json \
  --apple-id you@example.com \
  --sku towinly-ios-001
```

The two numbers above are Apple's own documentation examples and are not
Towinly values. Replace both.

Environment variables work when a flag is absent: `ASC_APP_ID`,
`APPLE_TEAM_ID`, `PLAY_SERVICE_ACCOUNT_KEY`, `APPLE_ID`, `IOS_SKU`.

What it does before writing anything:

- Refuses an `ascAppId` that is not digits, which catches the bundle identifier
  pasted into the wrong field.
- Refuses a Team ID that is not 10 upper case characters, which catches the one
  copied out of an email in lower case.
- Refuses a key file that is missing, is not JSON, is not a service account
  key, or has no `client_email`. An OAuth client file downloaded one menu away
  in the same console fails all of these.
- Refuses a key stored inside the app directory.

Every value is checked before a byte is written, and the write goes through a
temp file and a rename, so a refusal leaves `eas.json` exactly as it was.
`App/__tests__/fill-submit-config.test.js` proves each of those refusals and
proves the file is never left half written.

Exit codes: `0` written, `1` a value was refused and nothing changed, `2` the
`eas.json` given could not be read.

Read the diff before committing. The Play key path is written into a tracked
file. If EAS should hold the key instead, run `eas credentials -p android`,
upload it there, and remove `serviceAccountKeyPath` by hand.

## 5. The same thing by hand

For an edit at a keyboard rather than a command. Paste into `App/eas.json`,
replacing `"submit": { "production": {} }`.

```json
"submit": {
  "production": {
    "ios": {
      "appleId": "you@example.com",
      "appleTeamId": "ABCDE12345",
      "ascAppId": "1234567891",
      "sku": "towinly-ios-001"
    },
    "android": {
      "serviceAccountKeyPath": "/Users/you/.secrets/towinly-play-service-account.json",
      "track": "internal",
      "releaseStatus": "draft"
    }
  }
}
```

`track: "internal"` and `releaseStatus: "draft"` mean a mistyped command cannot
reach real users. Change the track deliberately, per release. `language`
defaults to `en-US`, so it is left out.

The first Android upload has to go through Play Console by hand. The Google
Play API starts working after one manual upload, so `eas submit -p android` is
useful from release two onward.

## 6. Owner actions: the free Expo account

None of this needs Apple money or a card. It does need a browser, so it cannot
run unattended. Do it before enrollment day.

```bash
cd "/Users/aghar/Documents/Projects/ToWin App/App"
eas login          # opens a browser, free Expo account
eas whoami         # confirm it prints an account name and not "Not logged in"
eas init           # writes extra.eas.projectId into app.json
```

Then review and commit the `app.json` diff. `eas init` also writes an `owner`
field when the account name differs from the slug. Accept it and commit it. The
slug `towinly` is frozen and locks at `eas init`. The `owner` field is not part
of the frozen set.

Until `eas login` runs, every command in section 4 still works, because writing
`eas.json` needs no account. Only the build and the submit need one.
