## Verified findings

### D2-01 [HIGH] Profile Edit sends Sex as 'Male'/'Female'/'Other' but the backend Gender enum only accepts MALE/FEMALE/OTHER, so every save that touches Sex is rejected 400 and nothing the elder typed is kept
**Location:** `app/profile-edit.jsx:311` · **Dimension:**  · **Status:** CONFIRMED
**Impact.** Any elder or helper who selects their Sex (a normal, offered profile field) and taps Save Changes gets 'Could not save right now. Please try again.' and loses that entire submission: the name, bio, interests, languages, occupation, social links, and date of birth in the same PUT are all discarded because the request never reaches the service. The elder cannot understand why an optional field silently breaks the whole form, and a user who previously set their Sex on the website sees it as blank on the phone, so they re-select it and hit the failure. Only users who never touch the Sex chips can save.
**Fix.** Store and send the enum name, not the display label. Model the chips like LOOKING_FOR does: `const GENDERS = [{ value: 'MALE', label: 'Male' }, { value: 'FEMALE', label: 'Female' }, { value: 'OTHER', label: 'Other' }]`, key the handlers and `aria-checked` off `value`, render `label`, and keep `gender: form.gender || null` in the save (now sending 'MALE'). This also fixes the prefill round-trip since `me.gender` already arrives as 'MALE'. Add a test that renders with `me.gender: 'MALE'`, asserts the Male chip is checked, and asserts the PUT body carries `gender: 'MALE'`.
**Verification.** Verified 2026-08-29 by hand: mobile GENDERS=['Male','Female','Other'] sends the display string 'Male' (profile-edit.jsx:42/311). The website sends 'MALE' (frontend ProfileEdit.jsx:465 <option value="MALE">Male</option>). Backend enum com/towinly/common/enums/Gender is MALE/FEMALE/OTHER; application.yml sets no accept-case-insensitive-enums and there is no Gender converter, so Jackson rejects 'Male'. Mobile-only: any Save with Sex chosen 400s and loses the whole form. The website is unaffected.

- [x] Fixed 2026-08-29: app/profile-edit.jsx now models the Sex chips as {value:'MALE',label:'Male'} like LOOKING_FOR; the PUT sends the enum value and a stored 'MALE'/'FEMALE' re-selects the chip. Test __tests__/profile-edit-gender.test.js (RED proved: sent 'Male', stored 'FEMALE' not selected).

### D2-02 [OPEN, deferred to the backend block work] [MEDIUM] Updates feed and home bell badge never apply the block list; a blocked person resurfaces with name, message preview and a chat deep-link
**Location:** `src/lib/updatesFeed.js:179` · **Dimension:**  · **Status:** CONFIRMED-MEDIUM
**Impact.** An elder who blocked a harasser still sees that person in the Updates center that the owner built as the one place for every notification: their new message rows (with the message preview text), a 'now friends' or friend-request row, their offers on help, and any review they left, and the home bell badge counts them. Tapping the message row opens the chat with the blocked person. This is the exact UGC 1.2 block promise that is enforced in the inbox, Offer Help, Friends discover and every trust panel, silently bypassed in the aggregated feed and its badge, on a trust-and-safety product for elders.
**Fix.** In useUpdatesFeed read the account's block list once (getBlocked(userId), the same ['block-list', userId] query the lists use) and filter the connections/needs/applications/reviews arrays by the blocked ids (matching filterBlocked's getId per source: otherUserId for connections, helperId/elderId for offers, reviewerId for reviews) before buildFeed, so a blocked person produces no Updates row and no bell count.
**Verification.** Verified 2026-08-29 by hand: updatesFeed.js has zero block references; buildFeed merges connection/message/applicant/offer/familyAlert/keyholder/review items with no client-side block filter. The /connections list is filtered server-side (ConnectionService.getMyConnections), so message and connection rows are safe, but review, keyholder-ask and family-alert sources are not proven to filter, so a blocked person can resurface in Updates through those. Defense-in-depth fix: filter buildFeed output against the device block list. Re-scoped from HIGH to MEDIUM because the highest-traffic source (connections) is already filtered.

### D2-03 [MEDIUM] Sealed box tells an elder "there is nothing in it yet" when the items fetch actually failed
**Location:** `src/components/passon/SealedItems.jsx:74` · **Dimension:**  · **Status:** CONFIRMED-MEDIUM
**Impact.** An elder who wrote down where her money/legacy is, opening the Sealed box on weak wifi to check it is still there, is told her box contains nothing. On the highest-stakes screen in the app this is the alarming false claim the codebase treats as a blocking rule (UX-706/AUD-102) everywhere else. No data is lost (a refresh restores it), but the momentary claim is exactly what the whole pattern exists to prevent.
**Fix.** Destructure isError and refetch from the passon-sealed query (pass-on/index.jsx:256) and, in the armed branch at :592, render `<LoadError what="your sealed box" onRetry={refetchSealed} bare />` when it failed instead of the SealedItems empty-state copy — the same shape already applied to setupFailed/keysFailed in this file.
**Verification.** Verified 2026-08-29 by hand: SealedItems.jsx:74 shows 'nothing inside' when items is empty. The parent pass-on/index.jsx:256 fetches ['passon-sealed'] WITHOUT isError, and the Sealed-box LoadError at :569 is gated on setupFailed (the ['passon-setup'] query), not the items query. If setup succeeds but the items fetch fails independently, the elder sees a false 'nothing inside' on the highest-stakes screen. Narrow (both usually fail together) so re-scoped to MEDIUM; fix: give ['passon-sealed'] its own isError and show LoadError.

- [x] Fixed 2026-08-29: pass-on/index.jsx gives ['passon-sealed'] its own isError+refetch and shows LoadError "your sealed items" when it fails, so an armed box whose items load fails never reads as empty. Test added to __tests__/three-states.test.js (RED proved against HEAD).
